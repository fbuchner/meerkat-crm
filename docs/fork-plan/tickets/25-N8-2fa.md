## Why this exists

There is **no second factor of any kind** today — verified: no TOTP, no MFA, no recovery codes anywhere
in the codebase. Authentication is password (bcrypt) or OIDC.

Worth noting explicitly: **Tier 1's full security review did not flag this.** It reviewed what existed
rather than what was absent, so this is a genuine new finding rather than a previously-accepted risk.
Weigh it accordingly — a self-hosted instance holding detailed personal data about people who never
consented to being in it is a meaningful target.

## What exists today

- `models.User` — `Password` (bcrypt; empty for OIDC-provisioned users), `TokenVersion` (added in Tier 1
  so a password change invalidates issued JWTs).
- `controllers.LoginUser` (`user_controller.go:82`) — accepts `identifier` (username or email, lowercased)
  or the legacy `email` field, with per-account rate limiting via
  `middleware.GetAccountRateLimiter()` and lockout after repeated failures.
- OIDC login path with PKCE, `azp`/`email_verified` handling, and RP-initiated logout.
- `models.ApiToken` with scopes (`full`, `carddav`) and expiry — the CardDAV credential path.

## What to build

1. **Schema**: TOTP secret (encrypted at rest, not plaintext), enabled flag, and **recovery codes**
   (hashed, single-use). Hand-written SQL migration.
2. **Enrollment flow**: generate secret → show QR + manual key → require one valid code to confirm before
   enabling → show recovery codes exactly once.
3. **Login flow**: after password verification, if 2FA is enabled, require a TOTP or recovery code before
   issuing the auth cookie. Do **not** issue a partially-authenticated session cookie.
4. **Disable flow**: require a current code or password re-entry.
5. **Frontend**: enrollment in Settings, the second-factor step on the login page, recovery-code display
   and regeneration.

## Traps

- **Do not require 2FA on the CardDAV/API-token path.** Those are non-interactive; that is exactly why
  scoped `ApiToken`s exist. Enforce 2FA on interactive login only, or you break every synced device.
- **OIDC users** have an empty password and their second factor belongs to the IdP. 2FA here should be
  unavailable or clearly separate for them, not silently bypassed in a way that surprises.
- **Rate-limit the code-verification step**, not just password entry. A 6-digit code is brute-forceable in
  minutes without it. The account rate limiter already exists — reuse it.
- Recovery codes must be **hashed** and single-use. Storing them in plaintext defeats the point.
- Clock skew: accept a ±1 step window, no more.
- `TokenVersion` should bump when 2FA is enabled or disabled, so existing sessions re-authenticate.

## Done when

- `go build ./... && go vet ./... && gofmt -l . && go test ./...` green.
- Tests cover: enrollment requires a valid code; login is blocked without the second factor; a recovery
  code works exactly once; the code step is rate-limited; a `carddav`-scoped token still authenticates
  CardDAV with 2FA enabled; an OIDC user's path is unaffected.
- Hand-verified: remove the second-factor check from the login path, confirm the block test fails,
  restore.
- Verified end to end in a real browser with a real authenticator app.

### Tests you must write before considering it done
- Backend: controller tests covering CRUD, ownership scoping, error states (not found, cross-user, 409 duplicate)
- Backend: real-DB test (`database.InitDB`, not `AutoMigrate`) for the core round-trip + any migration-dependent behavior
- Frontend: component test (`afterEach(cleanup)`, mock `fetch` with `vi.stubGlobal`) for dialog and list
- Hand-verify EVERY new test: break the code, confirm the test fails, restore. A test that has never failed has proven nothing.

### Self-verification checklist
1. `npx tsc --noEmit` — clean
2. `npx vitest run` — green (ALL tests, not just yours)
3. `cd backend && go build ./... && go vet ./... && gofmt -l . && go test ./...` — green
4. New migrations: run `make migrate-up` to verify they apply cleanly
5. All 5 locale files (`de/es/fr/it/en`) — real translations for any new strings

### Common traps (beyond CLAUDE.md)
- `gorm.Model` only works on uint-PK entities — UUID PK models need explicit `ID`/`CreatedAt`/`UpdatedAt` fields
- Backend tests use `setupRouter()` from `activity_controller_test.go` (sets `db`, `userID`, `cfg` in Gin context, uses AutoMigrate)
- Frontend component tests: `afterEach(cleanup)` mandatory; MUI appends `" *"` to required field `getByLabelText`
- Migration files: hand-written SQL up/down pairs — never add a column by editing the struct alone
- `gorm:"column:xxx"` tag is mandatory for acronyms/compound words — GORM silently derives wrong names
- New entities: decide soft vs hard delete per T26's rule (user-authored content → soft, edge/join rows → hard)
- Delete cascade: add new entities to `deleteContactAssociations` in `contact_controller.go` and `DeleteUser` in `admin_user_controller.go`
